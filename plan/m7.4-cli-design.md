# M7.4 design — the `doodle` CLI

A new `doodle` binary over `doodle-core` (Rust embedding API, **not** the C ABI;
placement `crates/doodle-cli/` per AD7). Subcommands `run` and `test` (the `repl`
AD7 names is **not** M7.4 scope). Ratified decisions below (D-M7-16..19 + riders,
user 2026-09-03); execute from this doc.

## Ratified decisions

### D-M7-16 — `time`/`random` are **real by default**; `--seed` day one (see discussions `c3ff96d`)

S-19/D-M7-4 already force `time`/`random` to be **suspending capabilities** (a
clock/RNG read can't be a synchronous FF — its result must cross the recordable
boundary, E§5.2/§5.3). That makes the resolution *policy* a pure UX call, and
real-by-default costs the determinism story nothing (any run is reproducible-in-
principle by recording/replaying the resolutions). So:
- `random` — default entropy-seeded; **`--seed N`** for a reproducible stream
  (ships day one; the "same maze every time" flag).
- `time` — real wall clock; **no fixed-time flag now** (faking time well is
  replay-tooling design, deferred).
- `--record`/`--replay` are the designated deterministic mode → the deferred E§11
  replay-artifact work, **not** a bespoke fixed-clock mode built now.
- **`doodle test` is unaffected**: the conformance harness resolves capabilities
  from scripted fixtures / the portable test registry (M7.5b), never the CLI's
  policy — so it stays deterministic by construction. (Don't "fix" it to real time.)
- CLI README line: real time/entropy enter *only* as capability resolutions, so a
  recorded run replays bit-for-bit — the policy is UX, the architecture is intact.

**Build:** two new engine capability constructors `time`/`random`
(`machine/intrinsic/`, `ForeignBody::Capability`, exported like `read_line_intrinsic`;
follow the zero-param `read_line`/`platform.rs` shape) + re-exports in `machine.rs`.
`read_line` already exists (a capability). The CLI resolves each by its
`CapabilityId` (the registration index; the CLI owns the index↔capability table).

### D-M7-17 — Un-bundle registration from load; the entry `module_path` is a real id (see discussions `ac2c013`)

E§3.2 already decides it: `load(instance, source, module_path)` where `module_path`
**is** the entry module's canonical id (the same identity imported modules get from
the resolver, S-21/S-63), and registration is a **separate pre-load step**
(S-43/E§5.5). The current public API fuses them (`load_with_intrinsics(module,
registry)` hardcodes the entry id to `"main"`) — an implementation gap against the
spec. **Fix the root cause, aligning the public engine API to the spec's factoring
(registration and loading orthogonal), not a combined loader variant or a CLI-side
`"main"→path` map** (which would falsify the S-63 record, side-channel the resolver
for relative imports, and misaddress S-21 breakpoints).
- **`"main"` dies as a magic default**: the engine defaults to *nothing*; each host
  supplies the entry id. The **wasm playground supplies its own id explicitly**; the
  CLI supplies the entry file's path; the C ABI keeps its own default constant (not
  the engine's magic name). Migrate all callers (wasm facade, conformance runner,
  capi, doodle-core tests).
- **Prefer un-bundling over a third entry point**: registration on the instance/
  registry, then `load(source, module_path)`. A test-only convenience may remain,
  but the *public* shape is the spec's. (Work out the minimal-ripple exact shape at
  implementation; if the reshape turns large, surface it before landing.)
- **Canonical-id normalization (the one subtlety):** the CLI mints a **normalized**
  entry id (absolute-resolved, no `..`) — but raw paths leak machine specifics.
  **M7.5d rider:** the trace schema renders module ids **entry-relative** (entry by
  bare name, imports relative to it), joining handle ids + foreign pointers on the
  exclusion-of-machine-specifics list — else three-surface transcripts differ by
  working directory.

### D-M7-18 — Drawing: the CLI is a real host with a **text sink**, not a no-op

Per M3.2 (turtle = Doodle over host primitives; each host renders as it likes),
the terminal CLI is a legitimate host that renders drawing to **text**. No-op
(silent discard, the S-10/S-56 family we've rejected) and exclude (the official CLI
can't run the official flagship library) both fail on principles used throughout.
- The CLI **registers** `draw_line`/`set_turtle`/`clear_canvas` and resolves them,
  accumulating into a draw sink.
- **Default human output:** a quiet, honest end-of-run summary — e.g.
  `drew 214 segments on a 400×400 canvas` — that tells the kid it *did* draw and
  where to see it properly (the browser).
- **`--draw-log`:** one deterministic line per draw command
  (`line (0,0)→(100,0) #000`) — what the gallery integration tests assert.
  Deterministic args ⇒ replay-stable log for free.
- **Cross-surface:** M7.5d's trace schema carries capability request identity +
  resolution, so a turtle fixture's draw sequence compares across native/wasm/C —
  drawing fixtures become conformance material, not CLI-only test value.
- **Never-silent rule:** any future discard-style sink (`--quiet`, headless) still
  counts + summarizes. One CLI README sentence: honesty is a contract, not a habit.
- **The gallery INCLUDES turtle programs** (the flagship the plumbing exists for),
  alongside terminal-friendly `print`/`read_line` programs.

### D-M7-19 — `doodle test` links the runner as a library

Refactor `tools/conformance-runner` to **lib + bin**: `lib.rs` exposes the
discovery/run API (`run(root) -> Result<fails, _>` etc.), the existing `main.rs`
becomes a thin wrapper, and `doodle-cli` depends on it and calls
`conformance_runner::run(root)` in-process (no subprocess, shared logic, directly
testable). Keep the runner's `demo_registry` parity intact.

## Smaller decisions (recommendations — proceed unless objected)

- **Arg parsing: hand-roll** (`std::env::args`, matching the runner + the audited
  minimal-dep house style / `deny.toml`), not `clap`/`lexopt`. Subcommands `run`/
  `test` + a few flags (`--seed N`, `--draw-log`) are small enough.
- **Streaming `print`: flush `output()` deltas between `run_slice` fuel steps** (or
  a final flush) — reuses the engine renderer; simplest. (A `Host` stdout callback
  is the fancier alternative, deferred.)
- **Exit codes / output:** `run` exits **0** on `Completed`, **nonzero** on
  `Raised`/`Faulted` (and load error); program `print` output → **stdout**;
  diagnostics/raise/fault renders → **stderr**, using `diag::render` (`SourceView` +
  `render_diagnostics`) for load errors and a matching snippet style (from
  `describe_raised` + `Trace.raised_at`) for runtime raises. `doodle test` mirrors
  the runner's exit code.

## What M7.4 builds

1. **Engine (doodle-core):** `time`/`random` capability constructors + re-exports;
   the **loader reshape** (D-M7-17: un-bundle registration/load, entry `module_path`
   parameterized, `"main"` default removed) + migrate callers (wasm facade,
   conformance runner, capi default, tests).
2. **conformance-runner → lib+bin** (D-M7-19).
3. **`crates/doodle-cli/`** (workspace member; `[[bin]] doodle`): `run` + `test`.
   - `run`: normalize→parse→resolve→load(registry `[print, read_line, time, random,
     draw_line, set_turtle, clear_canvas]`, entry path); drive `RunToCompletion`;
     loop resolving `Suspended` (by CapabilityId) + `SuspendedImport` (FS resolver);
     stream `print`; render `Raised`/`Faulted`/S-63 with spans; the draw sink
     (summary + `--draw-log`); `--seed`.
   - **FS resolver:** dotted `path` → `<importer_dir>/<seg>/….doodle`; importer dir
     via `Instance::module_canonical_id(ModuleId(req.importer))`; `canonical_id` =
     the normalized file path; `NotFound` when absent.
   - `test`: `conformance_runner::run(root)`.
4. **The minimal gallery** (under `examples/` per AD7): terminal-friendly programs
   (`print`/`read_line`/`time`/`random`) + turtle programs (via the draw sink) +
   CLI integration tests (gallery run with stable output, a multi-file import, a
   scripted `read_line`, `--draw-log` on a turtle program).
